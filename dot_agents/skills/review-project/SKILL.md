# Review a project

Honor any focus or boundaries the user supplies. Infer the project's purpose and intended users from targeted evidence in its README, examples, source, tests, configuration, and relevant history. Evaluate correctness, methodology, architecture, security where relevant, usability, documentation, tests, and practical value. Reproduce material claims or suspected defects when feasible without changing project files.

Return a concise review with these elements.

1. State the project's purpose, intended users, and evidence inspected.
2. Prioritize findings by severity. Distinguish confirmed defects, plausible risks, and preferences. Cite concrete files and lines, tests, or observed behavior and explain the user impact. Say if you found no material issues.
3. Identify strengths supported by the evidence.
4. Justify a score out of 10 and explain the effect of evidence gaps. Tie any path to a defensible 9/10 to specific quality improvements or additional evidence.
5. List only necessary fixes, ranked by impact and effort, with verification criteria.

Keep project files unchanged.
